\chapter{Project Overview}

\section{Project Title}
\textit{R2T-Based Differentially Private Query Evaluation on TPC-H}

\section{Background}

Differential privacy provides a formal way to release query answers while
limiting how much one private entity can affect the output. In a single
flat table, the sensitivity of a sum or count query is usually easy to
bound. In a relational database, however, one entity can be connected to
many secondary tuples through foreign keys. For example, in TPC-H one
customer may have many orders, and each order may have many lineitems.
If customer privacy is the target, removing one customer requires removing
all referencing orders and lineitems, so a join query can change by a
large amount.

The R2T paper, \textit{R2T: Instance-optimal Truncation for
Differentially Private Query Evaluation with Foreign Keys}, proposes a
Race-to-the-Top mechanism for this setting. The core idea is to use a
truncation threshold $\tau$ to limit the contribution of one private
entity, but to choose this threshold in a differentially private way.
Small thresholds produce low noise but high truncation bias. Large
thresholds preserve more of the true answer but require larger privacy
noise. R2T evaluates a geometric sequence of thresholds and returns the
best noisy, penalized candidate.

This project applies the R2T idea to the TPC-H benchmark. The goal is not
to build a general-purpose differentially private SQL engine. Instead,
the project implements two concrete TPC-H revenue cases as Python scripts,
records the intermediate R2T candidates, validates important invariants,
and produces reproducible output files.

\section{Project Scope and Objectives}

The project has four main objectives:

\begin{enumerate}
    \item Understand the R2T algorithm and how it applies to relational
    schemas with foreign-key relationships.
    \item Select two TPC-H cases that are representative but still small
    enough to implement directly.
    \item Implement the two cases as separate Python programs under a
    \texttt{code/} directory.
    \item Save results and provide a validation path so the output can be
    checked and reproduced.
\end{enumerate}

Both implemented cases use \texttt{Customer} as the private relation.
The protected unit is one customer together with the orders and lineitems
that reference that customer. The implemented queries are adapted from
TPC-H Query 3 and Query 5. They keep the important join structure and
selection predicates from the benchmark, but the final output is a scalar
revenue aggregate suitable for a single R2T release.

\section{TPC-H Cases Used in the Project}

The first case is a Q3-style customer revenue query. It joins
\texttt{Customer}, \texttt{Orders}, and \texttt{Lineitem}. The query keeps
customers in the \texttt{BUILDING} market segment, orders before
1995-03-15, and lineitems shipped after 1995-03-15. The revenue term is
\texttt{L\_EXTENDEDPRICE * (1 - L\_DISCOUNT)}.

The second case is a Q5-style ASIA revenue query. It joins
\texttt{Customer}, \texttt{Orders}, \texttt{Lineitem}, \texttt{Supplier},
\texttt{Nation}, and \texttt{Region}. It keeps orders in 1994, restricts
the region to ASIA, and requires the supplier and customer to come from
the same nation.

\chapter{Algorithm Design}

\section{Algorithm Overview}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.9\textwidth]{figures/algorithm_flow.pdf}
  \caption{Algorithm flow}
\end{figure}

The implemented pipeline follows the structure shown in Figure 2.1. For
each case, the program loads the required TPC-H \texttt{.tbl} files into
an in-memory SQLite database. It then executes a case-specific SQL query
that computes the revenue contribution for each customer. After this
preprocessing step, the R2T mechanism is applied to the list of
customer-level contributions.

Let $x_i$ denote the contribution of customer $i$ to the selected query.
For a threshold $\tau$, the truncated query answer is
\[
Q(I,\tau)=\sum_i \min(x_i,\tau).
\]
This form is valid for the two selected cases because they are
self-join-free and the privacy unit is the customer. In the general R2T
paper, a linear program is used for more complex queries, especially
self-joins or projections. For these two cases, the LP optimum reduces to
the same per-customer truncation form, so an explicit LP solver is not
needed.

\section{Algorithm Detail}

The project implements the following steps:

\begin{enumerate}
    \item \textbf{Source Loading}: Read selected TPC-H \texttt{.tbl} files
    using Python's standard \texttt{csv} module and insert them into an
    in-memory SQLite database.

    \item \textbf{Case Query Execution}: Execute one fixed SQL query per
    case. The output is grouped by customer key and contains one revenue
    value for each contributing customer.

    \item \textbf{Contribution Construction}: Convert the SQL output into
    a list of pairs \texttt{(customer\_key, contribution)}. The sum of all
    contributions is the non-private SQL answer.

    \item \textbf{Threshold Enumeration}: Generate candidate thresholds
    $\tau = 2,4,8,\ldots,2^{\lfloor \log_2(GS_Q)\rfloor}$. The default
    value is $GS_Q=10{,}000{,}000$.

    \item \textbf{Truncated Answer}: For each threshold, compute
    $\sum_i \min(x_i,\tau)$. This value is monotone in $\tau$ and never
    exceeds the original SQL total.

    \item \textbf{Noisy R2T Score}: Add Laplace noise and subtract the R2T
    penalty term. The score for threshold $\tau$ is
    \[
    \widetilde{Q}(I,\tau)
    = Q(I,\tau)
    + Lap\left(\frac{\log_2(GS_Q)\tau}{\epsilon}\right)
    - \log_2(GS_Q)\ln\left(\frac{\log_2(GS_Q)}{\beta}\right)
    \frac{\tau}{\epsilon}.
    \]

    \item \textbf{Final Output}: Return
    \[
    \max\left(0,\max_\tau \widetilde{Q}(I,\tau)\right),
    \]
    where $Q(I,0)=0$ because the revenue values are non-negative.

    \item \textbf{Result Saving}: Save the summary output as JSON and all
    candidate thresholds as CSV files under \texttt{results/}.
\end{enumerate}

\section{Implementation Details}

The implementation is divided into one shared utility module and two
case-specific scripts. The shared module \texttt{code/common.py} is
responsible for all steps that are common to both cases. The function
\texttt{load\_tables()} reads TPC-H \texttt{.tbl} files using the standard
Python \texttt{csv} module. Since TPC-H rows are separated by the
\texttt{|} character and end with a trailing separator, the loader inserts
\texttt{row[:-1]} into SQLite so that the final empty field is removed.
Each table is created with explicit TPC-H column names, which makes the
SQL queries readable and avoids relying on column positions later in the
program.

After the tables are loaded, each case script creates SQLite indexes on
the main join keys. For the Q3-style case, the indexes are on
\texttt{Orders(O\_CUSTKEY)} and \texttt{Lineitem(L\_ORDERKEY)}. For the
Q5-style case, extra indexes are created on
\texttt{Lineitem(L\_SUPPKEY)} and \texttt{Supplier(S\_NATIONKEY)}. These
indexes do not change the query result; they only make the full-data
experiment faster.

The function \texttt{customer\_contributions()} executes the SQL query and
returns a list of \texttt{(customer\_key, revenue)} pairs. This list is
the bridge between SQL processing and R2T processing. The non-private SQL
answer is simply the sum of these customer revenues. The private unit is
a customer, so the contribution list is also the unit on which truncation
is applied.

The function \texttt{r2t\_from\_contributions()} implements the actual
R2T loop. It first computes \texttt{log2(GS\_Q)}, then enumerates powers
of two by calling \texttt{tau\_candidates()}. For every threshold, it
computes the truncated value with:

\begin{lstlisting}[language=Python]
truncated = sum(min(value, tau) for _, value in contributions)
\end{lstlisting}

Then it samples Laplace noise using inverse transform sampling. A uniform
random value is transformed into a Laplace random variable, so no external
\texttt{numpy} dependency is required. The noisy R2T score is then
computed as:

\begin{lstlisting}[language=Python]
noise_scale = log_g * tau / epsilon
noisy_score = truncated + laplace(rng, noise_scale) - penalty_factor * tau
\end{lstlisting}

The best candidate is the row with the largest \texttt{noisy\_score}. The
final output applies the $Q(I,0)$ lower bound:

\begin{lstlisting}[language=Python]
r2t_output = max(best["noisy_score"], 0.0)
\end{lstlisting}

Finally, \texttt{save\_result()} writes two output files. The JSON file
stores the selected threshold, final R2T output, true SQL total, maximum
customer contribution, and parameters. The CSV file stores all candidate
thresholds, including the truncated answer, noise scale, and noisy score.
This makes the final result reproducible and inspectable instead of only
printing a terminal message.

\section{Q3-Style SQL Query}

\begin{lstlisting}[language=SQL]
SELECT
    c.C_CUSTKEY,
    SUM(l.L_EXTENDEDPRICE * (1.0 - l.L_DISCOUNT)) AS revenue
FROM Customer c
JOIN Orders o
    ON c.C_CUSTKEY = o.O_CUSTKEY
JOIN Lineitem l
    ON o.O_ORDERKEY = l.L_ORDERKEY
WHERE c.C_MKTSEGMENT = 'BUILDING'
  AND o.O_ORDERDATE < '1995-03-15'
  AND l.L_SHIPDATE > '1995-03-15'
GROUP BY c.C_CUSTKEY
HAVING revenue > 0;
\end{lstlisting}

This query is adapted from TPC-H Query 3. The original TPC-H Q3 reports
the top revenue orders. In this project, the same filtering and join path
are used, but the result is aggregated by customer because R2T protects
customer-level contribution.

\section{Q5-Style SQL Query}

\begin{lstlisting}[language=SQL]
SELECT
    c.C_CUSTKEY,
    SUM(l.L_EXTENDEDPRICE * (1.0 - l.L_DISCOUNT)) AS revenue
FROM Customer c
JOIN Orders o
    ON c.C_CUSTKEY = o.O_CUSTKEY
JOIN Lineitem l
    ON o.O_ORDERKEY = l.L_ORDERKEY
JOIN Supplier s
    ON l.L_SUPPKEY = s.S_SUPPKEY
JOIN Nation n
    ON c.C_NATIONKEY = n.N_NATIONKEY
   AND s.S_NATIONKEY = n.N_NATIONKEY
JOIN Region r
    ON n.N_REGIONKEY = r.R_REGIONKEY
WHERE r.R_NAME = 'ASIA'
  AND o.O_ORDERDATE >= '1994-01-01'
  AND o.O_ORDERDATE < '1995-01-01'
GROUP BY c.C_CUSTKEY
HAVING revenue > 0;
\end{lstlisting}

This query is adapted from TPC-H Query 5. The original TPC-H Q5 groups by
nation. This project keeps the ASIA-region and same-nation join logic but
aggregates revenue by customer first, which is required to apply the
customer-level R2T truncation.

\section{Implementation Structure}

The implementation is intentionally simple and direct. There is no query
parser and no general SQL rewriting module. The files are:

\begin{itemize}
    \item \texttt{code/common.py}: shared table loading, threshold
    generation, Laplace sampling, R2T scoring, printing, and result
    saving.
    \item \texttt{code/case\_q3\_customer\_revenue.py}: the Q3-style case.
    \item \texttt{code/case\_q5\_asia\_revenue.py}: the Q5-style case.
    \item \texttt{code/validate\_cases.py}: lightweight validation checks.
    \item \texttt{code/generate\_report\_figures.py}: figure generation
    from saved CSV/JSON results and saved contribution files.
\end{itemize}

The submitted implementation keeps the SQL case construction, R2T
threshold evaluation, validation checks, and figure generation inside
project-owned Python scripts. The runtime path does not require
\texttt{pandas}, \texttt{numpy}, or \texttt{pulp}.

\section{Input Design}

\begin{enumerate}
    \item Use the TPC-H \texttt{.tbl} files already available in
    \texttt{BDT\_IP\_Differential-privacy/data}. The tables used are
    \texttt{customer.tbl}, \texttt{orders.tbl}, \texttt{lineitem.tbl},
    \texttt{supplier.tbl}, \texttt{nation.tbl}, and \texttt{region.tbl}.

    \item Load only the tables required by each case. The Q3-style case
    loads \texttt{Customer}, \texttt{Orders}, and \texttt{Lineitem}. The
    Q5-style case also loads \texttt{Supplier}, \texttt{Nation}, and
    \texttt{Region}.

    \item Store tables in SQLite memory tables with explicit column names
    based on the TPC-H schema. This allows the SQL query to be written
    clearly and keeps the project independent from external database
    services.

    \item Create indexes on the main join keys, such as
    \texttt{O\_CUSTKEY}, \texttt{L\_ORDERKEY}, and
    \texttt{L\_SUPPKEY}. These indexes reduce the runtime of the full
    data query.

    \item Use fixed R2T parameters for reproducibility:
    $\epsilon=0.8$, $\beta=0.1$, $GS_Q=10{,}000{,}000$, and random seed
    1.
\end{enumerate}

\section{Answer Check Design}

The project includes a validation script:

\begin{lstlisting}[language=Bash]
python3 code/validate_cases.py
\end{lstlisting}

The validation checks are not a replacement for a formal proof, but they
verify important implementation properties:

\begin{enumerate}
    \item Each case produces at least one contributing customer.
    \item The true SQL total is positive.
    \item The truncated value is monotone non-decreasing as $\tau$
    increases.
    \item The truncated value never exceeds the original SQL total.
    \item The truncated value is bounded by
    $\tau \times$ the number of contributing customers.
\end{enumerate}

These checks passed for both implemented cases. This gives confidence
that the implementation follows the intended per-customer truncation
logic and that the candidate files are internally consistent.

More specifically, the validation script reruns both cases on a smaller
default sample and checks the following invariants inside
\texttt{validate\_result()}:

\begin{lstlisting}[language=Python]
assert result["private_entities"] > 0
assert result["true_total"] > 0
assert result["best"]["tau"] > 0

previous = -1.0
for row in result["rows"]:
    truncated = row["truncated"]
    tau = row["tau"]
    assert truncated >= previous
    assert truncated <= result["true_total"] + 1e-6
    assert truncated <= tau * result["private_entities"] + 1e-6
    previous = truncated
\end{lstlisting}

The first three assertions check that the SQL case and R2T selection
produce a meaningful result. The monotonicity check verifies the expected
mathematical property of $\sum_i \min(x_i,\tau)$: increasing $\tau$ cannot
decrease the truncated answer. The upper-bound check
\texttt{truncated <= true\_total} verifies that truncation never creates
extra revenue. The final bound
\texttt{truncated <= tau * private\_entities} verifies the privacy-side
constraint that each customer contributes at most $\tau$ after
truncation. When the validation script was executed, both cases returned
\texttt{ok}, confirming that these implementation-level checks passed.

\chapter{Conclusion}

\section{Conclusion}

This project successfully applied the R2T truncation mechanism to two
TPC-H revenue queries. The implementation protects customer-level
contribution, computes per-customer revenue, evaluates R2T threshold
candidates, adds calibrated Laplace noise and penalty terms, and saves
all outputs for later inspection.

The main result is that R2T selects intermediate thresholds rather than
the largest possible threshold. This behavior matches the intuition of
the algorithm: increasing $\tau$ reduces truncation bias but increases
noise and penalty. The final selected threshold balances these two
effects.

The project is intentionally limited to two concrete cases. It does not
try to support arbitrary SQL, self-joins, or projection-heavy SPJA
queries. However, it demonstrates the central R2T workflow clearly on
real TPC-H data and provides a reproducible code path, saved result files,
and generated figures.
