\chapter{Project Overview}

\section{Project Title}
\textit{R2T-Based Differentially Private Query Evaluation on TPC-H}

\section{Background}

This project started from a practical question: if the private unit is a
customer, how much can one customer change a join query on TPC-H?  For a
single table this kind of sensitivity bound is usually direct.  For
TPC-H it is less direct, because a customer can own many orders, and each
order can have several lineitems.  Removing one customer therefore also
removes the tuples that reference that customer.

The R2T paper, \textit{R2T: Instance-optimal Truncation for
Differentially Private Query Evaluation with Foreign Keys}, addresses
this problem by truncating private-unit contribution.  A small threshold
$\tau$ gives smaller noise but loses more of the query answer.  A large
$\tau$ keeps more revenue but also needs larger noise.  R2T tries powers
of two for $\tau$, adds noise and a penalty to each candidate, and then
returns the winner of this private race.

I did not try to build a full private SQL engine.  That would require a
much larger parser and query-rewriting system.  Instead, I selected two
TPC-H revenue queries where the private unit can be handled cleanly at
the customer level.  The code saves the intermediate candidate values, so
the result can be checked instead of only reported as a final number.

\section{Project Scope and Objectives}

The final scope was kept narrow on purpose:

\begin{enumerate}
    \item Use \texttt{Customer} as the private relation in both cases.
    \item Implement two concrete TPC-H-style revenue queries rather than
    a general query framework.
    \item Apply R2T to per-customer revenue contributions.
    \item Save enough intermediate output to make the experiment
    reproducible.
    \item Add a small validation script for the properties that are easy
    to check from the generated candidate files.
\end{enumerate}

The protected unit is one customer together with the orders and lineitems
that reference that customer.  The two implemented queries follow the
join and filter ideas of TPC-H Query 3 and Query 5, but they output one
scalar revenue value instead of the original benchmark outputs.  This
keeps the project focused on the R2T truncation mechanism.

\section{TPC-H Cases Used in the Project}

The first case is a Q3-style customer revenue query.  It joins
\texttt{Customer}, \texttt{Orders}, and \texttt{Lineitem}. The query keeps
customers in the \texttt{BUILDING} market segment, orders before
1995-03-15, and lineitems shipped after 1995-03-15. The revenue term is
\texttt{L\_EXTENDEDPRICE * (1 - L\_DISCOUNT)}.

The second case is a Q5-style ASIA revenue query.  It joins
\texttt{Customer}, \texttt{Orders}, \texttt{Lineitem}, \texttt{Supplier},
\texttt{Nation}, and \texttt{Region}. It keeps orders in 1994, restricts
the region to ASIA, and requires the supplier and customer to come from
the same nation.

\chapter{Algorithm Design}

\section{Algorithm Overview}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.9\textwidth]{figures/algorithm_flow.pdf}
  \caption{Algorithm flow}
\end{figure}

The pipeline in Figure 2.1 is the one used in the experiment.  Each case
loads only the tables it needs into an in-memory SQLite database.  The SQL
query then returns one row per contributing customer.  After that point,
the database part is finished; R2T only sees a list of customer revenue
values.

Let $x_i$ denote the contribution of customer $i$ to the selected query.
For a threshold $\tau$, the truncated query answer is
\[
Q(I,\tau)=\sum_i \min(x_i,\tau).
\]
This is the main simplification in the project.  The two selected cases
are self-join-free, and every released value is first reduced to a
customer contribution.  Under this setup, capping each customer's revenue
at $\tau$ gives the truncation function needed by R2T.  The full paper
uses LP formulations for more complicated settings, but those extra
pieces are not needed for these two selected queries.

\section{Algorithm Detail}

The implementation follows these steps:

\begin{enumerate}
    \item \textbf{Source Loading}: Read selected TPC-H \texttt{.tbl}
    files with Python's \texttt{csv} module and insert them into SQLite.

    \item \textbf{Case Query Execution}: Run one fixed SQL query per
    case.  The output is grouped by customer key.

    \item \textbf{Contribution Construction}: Convert the SQL rows into
    \texttt{(customer\_key, contribution)} pairs.  Their sum is the
    non-private SQL answer.

    \item \textbf{Threshold Enumeration}: Generate candidate thresholds
    $\tau = 2,4,8,\ldots,2^{\lfloor \log_2(GS_Q)\rfloor}$. The default
    value is $GS_Q=10{,}000{,}000$.

    \item \textbf{Truncated Answer}: For each threshold, compute
    $\sum_i \min(x_i,\tau)$. This value is monotone in $\tau$ and never
    exceeds the original SQL total.

    \item \textbf{Noisy R2T Score}: Add Laplace noise and subtract the R2T
    penalty term. The score for threshold $\tau$ is
    \[
    \widetilde{Q}(I,\tau)
    = Q(I,\tau)
    + Lap\left(\frac{\log_2(GS_Q)\tau}{\epsilon}\right)
    - \log_2(GS_Q)\ln\left(\frac{\log_2(GS_Q)}{\beta}\right)
    \frac{\tau}{\epsilon}.
    \]

    \item \textbf{Final Output}: Return
    \[
    \max\left(0,\max_\tau \widetilde{Q}(I,\tau)\right),
    \]
    where $Q(I,0)=0$ because the revenue values are non-negative.

    \item \textbf{Result Saving}: Save the summary, all candidate
    thresholds, and the customer contribution list under \texttt{results/}.
\end{enumerate}

\section{Implementation Details}

The code is split into a shared module and two case scripts.
\texttt{code/common.py} contains the loader, the R2T loop, printing, and
file output.  The loader reads the TPC-H \texttt{.tbl} files directly
instead of using a dataframe library.  TPC-H rows end with a trailing
\texttt{|}, so the loader stores \texttt{row[:-1]} in SQLite.  I used
explicit column names when creating each table, because it makes the SQL
queries easier to read.

After the tables are loaded, each case script creates SQLite indexes on
the main join keys. For the Q3-style case, the indexes are on
\texttt{Orders(O\_CUSTKEY)} and \texttt{Lineitem(L\_ORDERKEY)}. For the
Q5-style case, extra indexes are created on
\texttt{Lineitem(L\_SUPPKEY)} and \texttt{Supplier(S\_NATIONKEY)}. These
indexes do not change the query result; they only make the full-data
experiment faster.

The function \texttt{customer\_contributions()} is the boundary between
the SQL part and the R2T part.  It returns
\texttt{(customer\_key, revenue)} pairs.  Since the private unit is a
customer, this is also the right level at which to apply truncation.

The function \texttt{r2t\_from\_contributions()} implements the actual
R2T loop. It first computes \texttt{log2(GS\_Q)}, then enumerates powers
of two by calling \texttt{tau\_candidates()}. For every threshold, it
computes the truncated value with:

\begin{lstlisting}[language=Python]
truncated = sum(min(value, tau) for _, value in contributions)
\end{lstlisting}

Then it samples Laplace noise using inverse transform sampling. A uniform
random value is transformed into a Laplace random variable, so no external
\texttt{numpy} dependency is required. The noisy R2T score is then
computed as:

\begin{lstlisting}[language=Python]
noise_scale = log_g * tau / epsilon
noisy_score = truncated + laplace(rng, noise_scale) - penalty_factor * tau
\end{lstlisting}

The best candidate is the row with the largest \texttt{noisy\_score}. The
final output applies the $Q(I,0)$ lower bound:

\begin{lstlisting}[language=Python]
r2t_output = max(best["noisy_score"], 0.0)
\end{lstlisting}

Finally, \texttt{save\_result()} writes three output files.  The JSON
summary stores the selected threshold, final R2T output, true SQL total,
maximum customer contribution, and parameters.  One CSV file stores all
candidate thresholds, including the truncated answer, noise scale, and
noisy score.  The other CSV file stores the per-customer contributions.
This was useful for checking the result later and for drawing the
contribution concentration figure.

\section{Q3-Style SQL Query}

\begin{lstlisting}[language=SQL]
SELECT
    c.C_CUSTKEY,
    SUM(l.L_EXTENDEDPRICE * (1.0 - l.L_DISCOUNT)) AS revenue
FROM Customer c
JOIN Orders o
    ON c.C_CUSTKEY = o.O_CUSTKEY
JOIN Lineitem l
    ON o.O_ORDERKEY = l.L_ORDERKEY
WHERE c.C_MKTSEGMENT = 'BUILDING'
  AND o.O_ORDERDATE < '1995-03-15'
  AND l.L_SHIPDATE > '1995-03-15'
GROUP BY c.C_CUSTKEY
HAVING revenue > 0;
\end{lstlisting}

This query follows the filtering idea of TPC-H Query 3, but I aggregate
by customer instead of reporting individual orders.  That change is
needed because the privacy unit in this project is the customer.

\section{Q5-Style SQL Query}

\begin{lstlisting}[language=SQL]
SELECT
    c.C_CUSTKEY,
    SUM(l.L_EXTENDEDPRICE * (1.0 - l.L_DISCOUNT)) AS revenue
FROM Customer c
JOIN Orders o
    ON c.C_CUSTKEY = o.O_CUSTKEY
JOIN Lineitem l
    ON o.O_ORDERKEY = l.L_ORDERKEY
JOIN Supplier s
    ON l.L_SUPPKEY = s.S_SUPPKEY
JOIN Nation n
    ON c.C_NATIONKEY = n.N_NATIONKEY
   AND s.S_NATIONKEY = n.N_NATIONKEY
JOIN Region r
    ON n.N_REGIONKEY = r.R_REGIONKEY
WHERE r.R_NAME = 'ASIA'
  AND o.O_ORDERDATE >= '1994-01-01'
  AND o.O_ORDERDATE < '1995-01-01'
GROUP BY c.C_CUSTKEY
HAVING revenue > 0;
\end{lstlisting}

This query follows the ASIA-region and same-nation condition from TPC-H
Query 5.  The original query groups by nation.  Here the grouping is by
customer, again so that the contribution of one private customer can be
capped by R2T.

\section{Implementation Structure}

The implementation is intentionally direct.  There is no query parser and
no general SQL rewriting module.  The files are:

\begin{itemize}
    \item \texttt{code/common.py}: shared table loading, threshold
    generation, Laplace sampling, R2T scoring, printing, and result
    saving.
    \item \texttt{code/case\_q3\_customer\_revenue.py}: the Q3-style case.
    \item \texttt{code/case\_q5\_asia\_revenue.py}: the Q5-style case.
    \item \texttt{code/validate\_cases.py}: lightweight validation checks.
    \item \texttt{code/generate\_report\_figures.py}: figure generation
    from saved CSV/JSON results and saved contribution files.
\end{itemize}

The runtime path uses only the Python standard library and SQLite.  I
kept it this way so the experiment can run in a plain Python environment
without setting up extra numerical packages.

\section{Input Design}

\begin{enumerate}
    \item Use the TPC-H \texttt{.tbl} files stored in \texttt{data/}.
    The tables used are \texttt{customer.tbl}, \texttt{orders.tbl},
    \texttt{lineitem.tbl}, \texttt{supplier.tbl}, \texttt{nation.tbl},
    and \texttt{region.tbl}.

    \item Load only the tables required by each case. The Q3-style case
    loads \texttt{Customer}, \texttt{Orders}, and \texttt{Lineitem}. The
    Q5-style case also loads \texttt{Supplier}, \texttt{Nation}, and
    \texttt{Region}.

    \item Store tables in SQLite memory tables with explicit column names
    based on the TPC-H schema.  This keeps the SQL readable and avoids an
    external database service.

    \item Create indexes on the main join keys, such as
    \texttt{O\_CUSTKEY}, \texttt{L\_ORDERKEY}, and
    \texttt{L\_SUPPKEY}. These indexes reduce the runtime of the full
    data query.

    \item Use fixed R2T parameters for reproducibility:
    $\epsilon=0.8$, $\beta=0.1$, $GS_Q=10{,}000{,}000$, and random seed
    1.
\end{enumerate}

\section{Answer Check Design}

The project includes a validation script:

\begin{lstlisting}[language=Bash]
python3 code/validate_cases.py
\end{lstlisting}

The validation script is not a formal DP proof.  Its purpose is more
practical: rerun the two cases and catch mistakes in the truncation
values or saved candidate rows.  It checks:

\begin{enumerate}
    \item Each case produces at least one contributing customer.
    \item The true SQL total is positive.
    \item The truncated value is monotone non-decreasing as $\tau$
    increases.
    \item The truncated value never exceeds the original SQL total.
    \item The truncated value is bounded by
    $\tau \times$ the number of contributing customers.
\end{enumerate}

These checks passed for both implemented cases.  This is important
because the R2T mechanism relies on the truncated value being a stable
underestimate of the true answer.

More specifically, the validation script reruns both cases on a smaller
default sample and checks these invariants inside
\texttt{validate\_result()}:

\begin{lstlisting}[language=Python]
assert result["private_entities"] > 0
assert result["true_total"] > 0
assert result["best"]["tau"] > 0

previous = -1.0
for row in result["rows"]:
    truncated = row["truncated"]
    tau = row["tau"]
    assert truncated >= previous
    assert truncated <= result["true_total"] + 1e-6
    assert truncated <= tau * result["private_entities"] + 1e-6
    previous = truncated
\end{lstlisting}

The first three assertions check that the SQL query produced a usable
case and that R2T selected a positive threshold.  The monotonicity check
matches the formula $\sum_i \min(x_i,\tau)$: increasing $\tau$ cannot
decrease the truncated answer.  The upper-bound check confirms that
truncation never creates extra revenue.  The last bound checks that the
total capped contribution cannot exceed
$\tau \times$ the number of contributing customers.  When the script was
run, both cases returned \texttt{ok}.

\chapter{Conclusion}

\section{Conclusion}

The project implements R2T for two concrete TPC-H revenue queries with
customer-level privacy.  The important part is the reduction from a join
query to per-customer revenue contributions.  After that reduction, the
R2T threshold race can be implemented directly with
$\sum_i \min(x_i,\tau)$.

The experiment also shows the expected trade-off.  Larger thresholds keep
more of the true answer, but they increase both the penalty term and the
Laplace noise scale.  In both cases, R2T chooses an intermediate
threshold instead of the largest possible threshold.

The main limitation is that this is not a general private SQL engine.  It
does not handle arbitrary SQL, self-joins, or projection-heavy SPJA
queries.  Within the two selected cases, however, the implementation gives
a reproducible path from TPC-H tables to saved R2T outputs and figures.
